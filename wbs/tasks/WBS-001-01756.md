# 目的
容量削減、prototype専用bank-aware runtime、別分割方式を比較し、実装可能な方式を設計する。
# 作業内容
方式候補の容量、runtime compatibility、ROM header、影響範囲を比較する。
# 入力
01755のlayout evidenceとsound仕様。
# 成果物
解決方式設計。
# 完了条件
pointer access、ROM header、runtime影響、必要bank数を根拠付きで決定する。
# 完了にしてはいけない条件
Humanまたはproduction architectureの判断を無断で代行しない。
# 確認結果
生成ASMを実測し、sectionは0x84D9。内訳は固定pattern 173×64×3=
0x81C0、order/descriptor/instrument/routine/metadataの実directive 0x319、
wave 0x100、alignment 0x10である。dedup前0xB119からの削減後も16KBとの差は
0x44D9で、pulse1/pulse2/waveの行occupancyは83.81%/88.21%/91.04%だった。
固定64-row hUGEDriver contractのままの削減で収まる根拠はない。ROM0/ROMX、
driverのROM0配置、16-bit pointer、bank切替なし、ROM-only headerを確認した。
bank-aware driver、song分割、pattern単位bank、prototype別playerを比較したが、
production-like runtimeの変更、song境界の音楽的連続性、またはrepresentation選択に
Human判断が必要であり、01757へ進めず停止した。今回Humanから
「曲全体ではなく、何小節かだけ抜き出すようにしてください。」との判断があり、
評価scopeをfull-songからsource上の連続小節抜粋へ変更した。これは1-bank
full-song方式やmulti-bank方式の採用ではなく、既存ROM ONLY + hUGEDriverを維持して
自動編曲品質を評価するscope選択である。MBC、bank-aware runtime、production ROM
architecture、ArrangementPlan ruleは変更しない。詳細は
`docs/generated-pd-maple-leaf-rag-full-song-rom-layout-design.md`。
