## Sub-issueの構成案

Issue #1を移行全体の親とする。

1. **A. WBSの棚卸しと移行対応表の作成** — [Issue #2](https://github.com/ak-sekine/pocket-sweeper/issues/2)。今回作成した対応表を照合し、すべてのWBS ID・状態・関係・条件・参照を確定する。
2. **B. GitHub Issuesへの移行設計と実施計画の策定** — [Issue #3](https://github.com/ak-sekine/pocket-sweeper/issues/3)。Issue構造、粒度、依存関係、切替、検証、中断方法を決定する。
3. **C. 移行Issueの登録とWBSとの突合** — 承認後に未完了作業のIssueと必要なSub-issue/依存関係を登録し、CSVをIssue番号で確定する。
4. **D. 正本切替と運用文書の更新** — 移行登録・照合の承認後に限り、WBS履歴化と運用文書の更新を行う。
5. **E. 切替後の最終検証とユーザー受入** — Issue/WBS対応・リンク・状態・親子・証跡を確認し、切替承認を得る。

C〜Eは追加の提案であり、今回大量登録しない。GitHub REST APIのSub-issue一覧取得は確認でき、Issue #1の既存Sub-issueは作成前に0件だった。リポジトリ権限情報は`admin`、親Issueには`sub_issues_summary`があり、接続アプリには`issues:write`権限がある。一方、利用可能なGitHub連携ツールはIssue作成/更新とGET取得までで、正式なSub-issue追加操作を提供していない。CLIの`gh auth status`も`GH_TOKEN`が無効と報告した。このため、Issue #2と#3は作成したが、Issue #1の正式なSub-issueとしては登録できていない。Issue本文中の親候補記載は正式な親子関係ではない。GitHub UIまたは正式なSub-issue追加操作が利用可能になった時点で、#2と#3を#1に紐付け、API/UIから再取得して確認する必要がある。

## 依存関係と担当の表現

- WBS `parent` はIssueの親子と同一視しない。Issue構成は成果・完了条件から設計し、WBS対応表に元の親IDを保持する。
- WBS `depends_on` は118項目に記録されている。依存先が別Issueになった場合、GitHubの正式な依存関係機能が使えるときはそれを設定し、同時にIssue本文へ依存先番号と理由を残す。チェックリスト統合時は先行項目の完了条件を同一Issue内で順序づける。
- `blocked_by` は全件空。`depends_on`の意味を阻害関係と決めつけず、各依存辺を移行時に解釈する。
- Codex作業、`actor: human`作業、`actor_review_required`による要判断を本文上で分ける。人による実機、GUI、画像、音声確認は独立チェック項目または人担当Sub-issueとし、自動テストのみで完了にしない。
- 担当が文書と矛盾する項目、要件または証跡が未登録の項目は確認事項として残し、推測で担当・仕様・完了状態を変えない。

## 移行順序

1. 今回のA/Bで棚卸しと計画案をレビューし、ユーザーがIssue粒度・担当・未確定事項を承認する。
2. 承認された構成に沿って未完了WBSのみIssue化する。Issue作成ごとにWBS IDを付与し、分割・統合をCSVへ記録する。完了WBSは登録しない。
3. 既存Issueを再検索して重複を防ぎ、Issue作成後に番号・Open状態・本文・親子・依存関係を再取得する。
4. 全109未完了taskと20未完了groupを照合する。全taskにIssueまたはIssue内チェックリスト項目があり、groupが対応する成果Issueに追跡できることを確認する。
5. 人による作業・判断が未完了のまま保持されていることを確認する。Issue登録完了をユーザーレビューに出す。
6. 受入後にのみWBS正本からIssues正本へ切り替える。`AGENTS.md`・`PROJECT.md`・生成/検証ツールの変更は別の明示的な切替作業で行う。

## 重複防止

- 登録前に`repo:ak-sekine/pocket-sweeper is:issue`（open/closed両方）とWBS ID検索を実施する。
- Issueタイトルだけでなく、目的、完了条件、WBS IDを照合する。既存Issueへ統合する場合はその番号・理由をCSVへ記録する。
- Issue本文に旧WBS IDを明記する。分割・統合は対応表で全IDを列挙する。
- Issue作成と対応表更新の間に不整合が起きた場合、Issueを重複作成せず、再取得して既存番号を記録する。

## 正本切替と運用ルール案

移行前は`wbs/tasks/*.md`が唯一の進捗正本であり、Issuesは移行作業用である。大量登録後の照合とユーザーレビューが済むまではWBSを正本のまま保つ。切替時には、CSV対応表の確定版、移行時点のWBS一覧、Open/Closed状態、Sub-issue/依存関係の検証結果を保存し、ユーザー受入を記録してから運用文書を更新する。

切替後の案:

- GitHub Issuesが作業の状態・担当・完了証跡の正本。仕様の正本は引き続き`docs/*.md`。
- Issueには目的、WBS ID、参照仕様、成果物、完了条件、検証・証跡条件、担当区分を記載する。
- 人の確認を必要とする項目は確認者の記録を受けるまでOpenとする。
- WBSファイルと`reports/wbs.md`は履歴として保管し、正本切替後の状態更新には使わない。削除はしない。
- `AGENTS.md`と`PROJECT.md`、WBS validator/generatorの扱いは切替Issueで変更・検証する。今回変更しない。

登録後の検証:

- WBS全769 IDが対応表に一度だけ現れ、完了640/未完了129の分類が一致する。
- 未完了task109件すべてにIssueかIssue本文内チェックリストの正確な対応先があり、未完了group20件の成果も追跡できる。
- 親、依存、仕様、関連ファイル、担当、証跡条件を再取得データと突合する。Issue本文/番号が存在し、リンクが解決する。
- 既存Issue検索で重複がなく、正式なSub-issue関係をAPI/UIから確認する。本文リンクしか作れなかった場合は未達とする。
- Git差分では`git diff --check`と、変更した資料のリンク・CSV ID一意性・分類検査を行う。ゲーム実装や仕様テストは移行資料だけの変更時には行わない。

途中中断ではWBSを正本として維持する。Issue作成済みなら既存Issueを閉じたり削除したりせず、対応表へ番号・状態・理由を記録し、ユーザー承認を得るまで再開・大量登録・運用切替を止める。切替後に問題が見つかった場合は、WBS履歴を復元元にし、Issuesと対応表を照合して、ユーザー判断のもとで一時的にWBS正本へ戻す。Issueを一括削除してロールバックしない。
